# 一、大模型选型评估

> 面试91%的人员都会问到，务必具备完整方法论。虽然不一定每次项目都做，但必须懂。

## 1.1 为什么要做选型评估？

**核心观点**：

- **野路子 vs 正规军**：小公司可能由算法直接决定（野路子），但简历和求职中必须由PM主导或参与选型（体现专业性）。
- **协作模式**：PM不是一言堂，需与研发、算法、训练师共同评估。PM提供场景和数据评测集，算法负责跑模型。

**不同场景下是否需要做大模型选型评估？**

| 场景类型                                                        | 是否做评估选型                   | 原因说明                                                                             |
| :-------------------------------------------------------------- | :------------------------------- | :----------------------------------------------------------------------------------- |
| **自研AI产品/SaaS** `<br>`(没有自研大模型的互联网公司)          | ✅**必须**                        | 用大模型做产品开发，模型性能决定产品体验，需要综合评估（准确率、成本、接口稳定性等） |
| **大模型公司的产品** `<br>`(阿里、百度、字节、大模型6小龙等)    | ❌**无需选型** `<br>`(用自家模型) | 默认只能接自家大模型 `<br>`*(注：偶尔有例外，如内部模型效果太差时)*                  |
| **企业级私有部署** `<br>`(金融、政务、医疗、新能源等甲方)       | ✅**需要**                        | 通常不能用开放API，要选能落地部署的开源或国产模型（信创/合规要求）                   |
| **内部探索验证 / Demo / PoC** `<br>`(包括在Coze/Dify上搭建产品) | ✅**可选型但不需重流程**          | 轻量比较几个模型的实际效果，用于探索性试错，关注流程跑通                             |

## 1.2 选型方法论：4看1测 + 成本考量

**核心口诀**：**4看 + 1测 + 成本考量**

### 1.2.1 四看（辅助参考）

1. **看榜单**

   - **SuperCLUE**（国内最权威）：中文大模型综合性测评基准，关注季度/半年度报告。聚焦推理、数学、代码、智能体等任务。
   - **LMSYS Chatbot Arena**   https://lmarena.ai（社会/民间组织）：用户投票（Blind Test），代表“民意”。
   - ⚠️ **注意**：榜单仅供参考，排名高不代表业务落地效果好。
2. **看训练数据**

  - **通用文本** (基础语言能力)：
    - 英文：Common Crawl, Wikipedia, The Pile
    - 中文：WuDaoCorpora, WanJuan 等
  - **领域专用** (垂直行业能力)：

    - 代码：GitHub公开代码

| **豆包**     | 万亿级年轻化+多模态语料         | **字节跳动生态内**短视频字幕、直播评论、社交聊天数据。结合公开网文、新闻。侧重“**年轻化表达**”“创意生成” (如文案、故事、短视频脚本)。多模态能力 (图文理解、视频帧解析) 持续迭代，适合C端娱乐、营销内容生成。 |

- 💡 **提示**：如果你的业务是垂直行业，优先选择领域专用数据集覆盖较好的模型。

3. **看客户案例**

   - 关注官网“行业解决方案”。
   - 查看是否有同行业**标杆客户**（如有教育落地代表有该领域经验）。
   - 查看**中标金额**（To B/G端可查招投标），侧面印证实力。
4. **看模型类型（指令 vs 推理）**

**选择逻辑：指令模型 还是 推理模型？**

1. **任务复杂度**
   - **明确、有标准答案**：用 **指令模型** (如 GPT-4o mini, DeepSeek V3)。
   - **需要逻辑推理、多轮推断**：用 **推理模型** (如 DeepSeek R1, Gemini 2.5-Thinking, Kimi-k2-Thinking)。
2. **是否需要解释性**
   - 如果需要输出**理由、过程、判断路径**：用 **推理模型**。
   - 如果只需要**结果** (如分类、摘要)：用 **指令模型**。
3. **延时与成本容忍度**
   - **实时交互产品** (AI客服、问答助手)：优先 **指令模型**。
   - **后台异步任务** (报告生成、智能规划)：可以选 **推理模型**。

| 模型类型                                        | 核心能力                                    | 特点                                          | 适用场景                                                                   | 成本/速度          |
| :---------------------------------------------- | :------------------------------------------ | :-------------------------------------------- | :------------------------------------------------------------------------- | :----------------- |
| **指令模型** `<br>`(Instruction Model)          | **按照提示精确执行**                        | 听话，不思考                                  | 明确任务、格式化输出 `<br>`(如分类、摘要、意图识别、简单问答)              | **成本低，速度快** |
| **推理模型** `<br>`(Reasoning / Thinking Model) | **具备思考链路** `<br>`能解释原因、规划步骤 | 会思考，速度很慢 `<br>`(Thinking过程不可跳过) | 复杂决策、多步推理、开放任务 `<br>`(如代码生成、数学问题、复杂的Agent规划) | **成本高，延时长** |

**典型业务场景的模型选择示例**：

| 业务场景                  | 模型类型     | 理由                       |
| :------------------------ | :----------- | :------------------------- |
| **电商客服意图识别**      | **指令模型** | 规则明确、延时敏感         |
| **智能写作/总结报告**     | **推理模型** | 需要生成具备逻辑结构的长文 |
| **数据分析问答 (ChatBI)** | **推理模型** | 需要多步推理与SQL规划      |
| **FAQ问答**               | **指令模型** | 先检索再生成答案，路径确定 |

> 📌 **原则**：**能用指令模型解决的，不要上推理模型**

- **DeepSeek V3** 是指令模型；**R1** 是推理模型。
- ⚠️ **误区**：意图识别不要用推理模型（大材小用，延时高）。

### 1.2.2 一测（核心关键）

**实测原则**：

- **真实场景数据**验证实际效果。
- 榜单提升2%在业务中感知不强，必须用业务数据测。

**评估步骤（5步法）**：

* 1.明确场景和任务目标（AI产品经理）
* 2.构建真实业务数据测试集（AI产品经理&运营）
* 3.确定评估标准（AI产品经理）

  * 1)指令遵循性（听话）
  * 2)业务理解力（懂场景）
  * 3)成本与延时（能否上线）
* 4.调用模型验证测试（算法）
* 5.评估效果并决策（AI产品经理&算法）

1. **你的场景和任务目标** —— (角色: AI产品经理)
   - **示例（电商客服退换货场景意图定义）**：

| 问题类型 / 意图  | 对话示例                                       |
| :--------------- | :--------------------------------------------- |
| **退货政策咨询** | “我买的衣服不合适，能退货吗？”                 |
| **售后流程问询** | “我要怎么申请换货？”                           |
| **订单物流查询** | “我想问一下我的退货物流什么时候能上门取件？”   |
| **商品问题**     | “你们卖的这个手机是正品吗？”                   |
| **售后联系方式** | “你们的售后客服电话是多少？我要直接打电话沟通” |
| **发票开具**     | “怎么申请电子发票？”                           |
| **情绪投诉类**   | “你们平台太慢了，我很不满意”                   |

2. **构建真实业务数据测试集** —— (角色: AI产品经理 & 运营/标注)

> **金标集 (Golden Dataset)** = “带有人工确定的标准答案”的数据集

- **a. 问题收集/来源方式**：
  1. 历史真实客服对话记录（需要整理/清洗）。
  2. 用户商品评价或客服工单（需要整理）。
  3. 运营/客服提供的典型/高频问题。
  4. 让大模型做扩写（*⚠️注意：仅在数据极缺时使用，一般优先用真实数据*）。
- **b. 数据量级**：
  - 假设每个意图收集 5-10 条数据。
  - 总量一般 **几百条 - 几千条** 不等，视业务覆盖度而定。
- c.构建高质量测试数据集—5大原则：*好数据集 ≠ 多*

| 原则    | 说明                                         | 示例                                   |
| :------ | :------------------------------------------- | :------------------------------------- |
| ✅**准** | 每条样本必须有明确标签（意图），不能模糊不清 | “我要开发票” → 发票开具                |
| ✅**广** | 覆盖所有主力意图类型，兼顾少量长尾意图       | 商品问题、售后流程、情绪投诉           |
| ✅**真** | 样本应来源于真实用户表达，模拟场景真实       | 从历史工单脱敏或运营总结而来           |
| ✅**难** | 包含模糊表达、方言、多意图、跳跃式表达       | “我要退了，但地址不是我选的，咋回事？” |
| ✅**稳** | 每类样本数量均衡、表达多样，避免单一模板化   | 发票类不能全是“怎么开发票？”           |

- **注意**：此原则同样适用于**模型微调(Fine-tuning)**训练集的要求。
- **避免**：尽量不要用大模型大量扩写评测集（不仅不准，且同质化）。
- **示例（金标集数据样例）**：

| ID   | 意图类型 (标注/标准答案) | 用户问题                         |
| :--- | :----------------------- | :------------------------------- |
| Q001 | **退货政策咨询**         | 我买的衣服太小了，想退货可以吗？ |
| Q002 | **退货政策咨询**         | 不满意这个款式，能退吗？         |
| Q003 | **退货政策咨询**         | 买回来后发现质量不好还能退吗？   |
| Q006 | **售后流程问询**         | 申请换货的流程是什么？           |
| Q007 | **售后流程问询**         | 在哪里可以操作换货？             |
| Q011 | **订单物流查询**         | 我退的东西快递还没来取，正常吗？ |
| Q012 | **订单物流查询**         | 退货快递单号在哪里可以查？       |
| Q026 | **发票开具**             | 订单完成后还能开发票吗？         |
| Q031 | **情绪投诉类**           | 你们服务太差，我很不满意！       |
| ...  | ...                      | ...                              |

3. **确定评估标准** —— (角色: AI产品经理)

- 重点关注：指令遵循性(听话)、业务理解力(懂场景)、成本与延时(能上线)。
- **核心任务**：以【意图识别分类准确性】评估为例（电商客服退换货场景）

| 指标名称            | 含义                                    | 计算方法 (示例)                                                 |
| :------------------ | :-------------------------------------- | :-------------------------------------------------------------- |
| **准确率 (总体)**   | 所有预测中，预测正确的占比              | `预测正确数 / 总样本数<br>`例：预测35条，正确29条，准确率=82.9% |
| **准确率 (分意图)** | 某类样本中，预测正确的占比              | `某类中识别正确数 / 该类样本总数`                               |
| **误识别率**        | 被预测为错误类别的样本占比              | `错误预测数 / 总预测数<br>`例：把“情绪投诉”误认为“退货咨询”     |
| **空识别率**        | 模型未能给出明确结果(拒答/未识别)的占比 | `结果为空的样本数 / 总样本数`                                   |

- **客观指标**：准确率、召回率、误判率、空识别率。
- **主观指标**：业务理解力、指令遵循、风格符合度。

4. **调用模型验证测试，跑结果** —— (角色: 算法)

   * 交给算法团队，在备选模型（A/B/C）上跑同一套评测集和Prompt。
   * **控制变量**：同一份数据、一致的Prompt、统一评估维度。
5. **评估效果，做出模型选型决策** —— (角色: AI产品经理 & 算法)

   - **决策**：结合效果数据与成本分析，选出最优模型。
   - **实战案例数据**（电商退换货意图识别）：

| 项目              | 模型A (高性能) | 模型B (低成本) | 模型C (平衡型) |
| :---------------- | :------------- | :------------- | :------------- |
| **准确率**        | **88%**        | 75%            | 82%            |
| **空识别率**      | **3%**         | 12%            | 6%             |
| **情绪类召回率**  | **80%**        | 55%            | 70%            |
| **平均响应时间**  | 2.5s           | **0.9s**       | 1.6s           |
| **平均Token消耗** | 1200           | 600            | 900            |
| **平均调用成本**  | 0.024元/次     | **0.012元/次** | 0.018元/次     |
| **月度预估成本**  | 4.8万元        | **2.4万元**    | 3.6万元        |

- **决策逻辑**：
  - 如果是**核心体验场景**（如纠纷处理），优先选 **A**（准确率至上）。
  - 如果是**高并发低价值场景**（如闲聊/简单查询），优先选 **B**（成本优先）。
  - 通常企业会追求 **性价比**，或者采用 **大小模型结合** 策略。

### 1.2.3 成本考量（ROI）

**核心逻辑**：**脱离成本谈效果是耍流氓**。

**ROI决策矩阵**：

| 成本维度             | 决策点                             | AI产品经理关注点              |
| :------------------- | :--------------------------------- | :---------------------------- |
| **模型调用成本**     | 一次调用多少钱？Token单价多少？    | 控制Token消耗，评估调用频次   |
| **计算资源成本**     | 自建 vs 托管？并发性能够不够？     | 看GPU成本、推理延时、并发瓶颈 |
| **数据准备成本**     | 数据获取难不难？标注与清洗难不难？ | 人工评估 + 数据集的维护成本   |
| **投资产出比 (ROI)** | 提效多少？降本多少？               | 衡量模型投入产出比            |

> 📌 **核心结论**：**最贵的模型 ≠ 最好用的模型**。能稳定解决业务问题、可控成本的模型才是最优解。

- **决策平衡**：模型A（90%准，贵，慢） vs 模型B（88%准，便宜，快）。企业通常选**B**（性价比高，够用）。

**实际场景中，选择多大参数规模的大模型？**

| 任务类型                           | 示例                           | 推荐模型规模                                  | 原因说明                                       |
| :--------------------------------- | :----------------------------- | :-------------------------------------------- | :--------------------------------------------- |
| **文本分类 / 情感分析 / 意图识别** | 评论正负面识别、客服问题归类   | **小型模型 (1B~7B)**                          | 模型对语义理解要求中等，追求速度与成本         |
| **简单信息抽取**                   | 抽取人名、地名、组织名等       | **中小型模型 (1B~13B)**                       | 抽取偏结构化的信息，任务确定性高               |
| **问答**                           | 简单问题                       | **中型模型 (13B~30B)**                        | 需要一定的知识储备和上下文理解能力             |
| **开放式生成**                     | 写文章、起标题、写剧本、编故事 | **大型模型 (30B~70B+)**                       | 对语言流畅性、创造力和语义一致性要求高         |
| **多轮对话 / 复杂逻辑推理**        | AI客服/智能助理/长上下文对话   | **超大模型 (70B+)**`<br>`结合RAG+必要时微调   | 涉及上下文记忆、推理链条，需要高容量和推理能力 |
| **代码生成 / 数据分析 / SQL编写**  | 让AI写函数或分析报表           | **大模型 (30B~70B+)**`<br>`结合RAG+必要时     | 模型具备结构化语言知识，处理复杂语义           |
| **行业定制任务** (如医疗、金融)    | 医学问答、金融知识匹配         | **大模型 (30B~70B+)**`<br>`结合RAG+必要时微调 | 需要基础通用能力+专业知识迁移                  |

💡 **经验总结**：

- **大模型**适合做**探索性任务**（如生成、创意、复杂推理）。
- **小模型**适合做**确定性任务**（如分类、抽取、简单问答）。
- ⚠️ **注意**：模型参数仅做参考，**测试验证**才是最后决策关键。

### 1.2.4 拓展：免费开源模型 vs 商业托管(闭源)模型

| 对比项           | 免费开源模型 (自行部署)                                 | 商业托管模型 (按调用付费)                                  |
| :--------------- | :------------------------------------------------------ | :--------------------------------------------------------- |
| **成本结构**     | **0元模型本身成本**，但需要自建算力，投入部署和维护成本 | 按调用次数/Token收费，**前期成本低**但长期使用成本可能较高 |
| **部署灵活性**   | **高**，可私有化部署在本地或自选云平台                  | 低，受制于服务商 API 提供的能力与接口                      |
| **安全与合规**   | **高**，可本地部署，便于满足金融/政企数据安全和合规要求 | 需评估数据出境/传输安全问题，**敏感行业有风险**            |
| **可控性**       | **高**，可微调、自定义推理逻辑或 Prompt 管理            | 低，大多无法修改模型本体，只能通过 Prompt 控制             |
| **性能优化**     | 可自行调优、更贴合特定业务 (如金融行业术语)             | 泛用性强，调优依赖服务商支持                               |
| **模型版本更新** | 需人工更新和运维，**技术门槛较高**                      | 服务商定期自动更新，无需自行维护                           |
| **使用门槛**     | **高**，需要懂模型推理框架、MLOps、推理优化等           | **低**，API调用即可，适合快速上线 MVP                      |
| **落地速度**     | 慢，准备周期长，需要运维配合                            | **快**，适合验证场景、跑通业务流程                         |
| **适合场景**     | **数据敏感、需要行业定制、重视长期成本控制的企业**      | **初创项目、快速验证场景、非核心敏感业务**                 |
| **模型举例**     | LLaMA系列、ChatGLM、DeepSeek (开源版)                   | GPT-3.5 / GPT-4、文心一言 (API版)                          |

> 📌 **选择建议**：
>
> - MVP阶段/验证想法：首选 **商业API**（快、省心）。
> - 核心业务/数据敏感/长久运营：逐步切换为 **开源自部署**（安全、可控、长期便宜）。

## 1.3 选型总结

> **最优选型 = 效果 × 成本 × 业务匹配度**
>
> **核心**：哪个模型最适合你的业务、最划算、最能落地。

| 环节           | 核心问题                 | AI产品经理要做的具体事项                      |
| :------------- | :----------------------- | :-------------------------------------------- |
| **看榜单**     | 哪些模型表现强？         | 对比公开评测榜（SuperCLUE / Arena），筛出候选 |
| **看数据**     | 模型懂不懂业务？         | 分析模型训练语料，判断是否覆盖你所在领域      |
| **看案例**     | 谁在用？用得好吗？       | 参考客户案例与行业落地情况，判断可复制性      |
| **看模型类型** | 用指令模型还是推理模型？ | 结合任务复杂度与业务时延要求具体判断          |
| **一测**       | 实际业务跑得怎么样？     | 用真实业务数据评测集对比效果与延时            |
| **成本考量**   | 效果与成本哪个最优？     | 综合Token成本、响应速度、ROI计算，做最终决策  |

# 二、需求分析

## 2.1 需求分析核心四问（详细拆解）

**1. 用户是谁 (User)**

> *“泛用户” = 没有优先级；AI产品要锁定明确的第一批目标用户。*

- **用户身份**：是公司员工？运营？C端用户？管理者？开发者？
  - **注意**：区分**客户 (Customer)** 与 **用户 (User)**。
    - ToB场景中，产品做给谁用 ≠ 谁买单。
    - 例：**钉钉**的客户是老板（买单，关注管理效率），用户是员工（使用，关注好用不卡）。
  - **思考**：做电商AI客服系统，你的目标用户是客服人员（提效工具），而非C端买家。
- **用户画像**：经验水平？技术背景？岗位职责？
  - **思考**：法律法规AI问答，对标用户如果是**律师**（专业工具，要求严谨、引用法条），与对标**普通大众**（普法咨询，要求通俗易懂），产品设计完全不同。

**2. 使用场景 (Scenario)**

> *如何触发 / 什么端 / 什么接入方式使用这个产品？*

- **举例（电商AI客服助手）**：
  - **时间 (When)**：双11/618大促期间，客服人力不足。
  - **触发 (Trigger)**：系统自动对用户问题做意图识别，辅助转交给对应处理流程。
  - **端 (Where)**：单独Web网页 / 嵌入在CRM系统内 / 微信小程序？
  - **接入方式 (How)**：主动打开 vs 被动提示？
    - *被动提示*：客户发消息后，系统自动识别意图并推荐“处理建议”或“快速回复模板”供客服参考（Copilot模式）。

**3. 真实问题与可行性 (Feasibility)**

> *当前问题大模型能否有效解决？“能做”不代表“值得做”。*

- **核心判定**：AI是否稳定、可控、可评估、低成本。
- **三大适配场景**（回顾AI案例课）：
  1. **语言密集型**：依赖大量文本、语音、对话、文书的流程。
  2. **人效低但可标准化**：内容产出任务（如写SEO水文）。
  3. **认知过载**：信息汇总场景（如会议纪要、财报分析）。
- **技术追问**：
  - 能通过 Prompt / RAG / 微调 等方式提升效果吗？
  - 模型效果能达到可接受水平吗？（如95%准确率）

**4. 需要哪些AI功能/工具？**

- 根据上述分析，确定是需要对话功能、生成功能、还是后台分析功能。

## 2.2 案例延伸：AI会议总结助手（案例详解）

| 核心4点               | 内容说明                                                                                                                                                                            |
| :-------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **用户是谁?**         | **公司职场人** (HR、产品、运营) 打工牛马，负责开会、整理、发纪要的人                                                                                                                |
| **要解决的问题?**     | 1. 每次会议内容杂、结构乱。`<br>`2. 手动整理纪要费时费力。`<br>`3. 需要自动抓重点、按议题分段、自动输出总结。                                                                       |
| **AI大模型能解决么?** | -**语言密集型**的场景 `<br>`- **可标准化**的内容产出任务 `<br>`- **认知过载** `<br>`*(之前讲过的LLM 3个使用场景)*`<br>`👉 是自然语言任务，可用 **转录+LLM生成摘要总结** 的能力解决。 |
| **对应功能**          | 会议内容转写 `<br>`会议摘要                                                                                                                                                         |

**高阶需求演进**：

1. **从信息转为 Action**：提取“待办 (To-Do)”，打通OA/钉钉，自动创建任务并@责任人。
2. **从通用转为垂直**：政务、医疗、金融专用（如提取营收数据、同比环比等结构化指标）。
3. **从文本摘要到结构化数据**：提取关键数据表（如财报会议中的营收、净利润等）。

**案例：AI会议总结助手 (自动提取QA对) 的完整迭代分析**

**Phase 1: 产品探索 (确认“QA对”是否为真实需求)**

- **需求调研**：访谈10位PM/项目经理，分析3场会议记录。
- **发现痛点**：
  - “回头想查谁说了什么，Ctrl+F翻半天”（检索困难）。
  - “不需要看全纪要，只想知道决策是什么？谁做？”（目标导向）。
  - “能不能像文档助手那样，问一句就告诉我答案？”（期待交互式反馈）。
- **初步结论**：用户更倾向于 **“问答式理解会议内容”**，而非线性通读纪要。

**Phase 2: 验证阶段 (验证该能力是否被广泛接受)**

- **调研方法**：问卷调查(500人 ToB企业客户)、Demo投放测试。
- **调研结果**：
  - 认可“QA形式更方便”的比例：**64.20%**
  - 使用过AI纪要的用户中愿意尝试QA版的比例：**71%**
  - 表示“愿意通过提问获取会议内容”的用户：**>73%**

**Phase 3: 迭代阶段 (验证功能是否“可用、好用、复用”)**

- **调研方法**：A/B测试 (普通摘要 vs QA结构化)、后台日志分析。
- **AB实验设计**：
  - **A组 (对照组)**：普通会议摘要文本 (按时间线)。
  - **B组 (实验组)**：提炼会议QA结构 (10-15条问答，如：谁负责？结果是什么？)。
- **数据表现**：

| 行为项              | 数据表现         | 洞察分析                        |
| :------------------ | :--------------- | :------------------------------ |
| **QA查看率**        | **85.40%**       | 用户对问答结构高度关注          |
| **“点赞”行为**      | 平均**2.3条**/会 | 表明有判断“有用”的行为意愿      |
| **“划线/复制”**     | 增长**23%**      | 用户倾向于拿“答”复制发群/汇报   |
| **“追问/点击溯源”** | 占比**27%**      | 有部分用户想深入追溯原文/上下文 |
| **“踩”行为**        | 占比仅**4%**     | 错误率控制良好，用户接受度高    |

**不足与机会**：

- **垂类机会**：金融/医疗专用会议系统（提取特定业务数据、结构化入库）。

## 2.5 常见需求调研方法分类

| 调研方法                | B端 / C端 | 定性 vs 定量 | 目标/观点 vs 行为/事实 | 样本大小  | 阶段       | 核心输出                             | 适用场景 (示例)                        |
| :---------------------- | :-------- | :----------- | :--------------------- | :-------- | :--------- | :----------------------------------- | :------------------------------------- |
| **录像日记 / 影像观察** | Both      | **定性**     | **行为/事实**          | 5-10人    | 上线后验证 | 真实场景下的使用流程与痛点           | 做客服系统，在客服人员电脑上装录屏软件 |
| **后台数据分析**        | Both      | **定量**     | **行为/事实**          | 全量日志  | 迭代阶段   | 用户路径、漏斗转化、留存率、停留时长 | **所有AI产品都要做** (RAG指标上报)     |
| **A/B 测试**            | C端       | **定量**     | **行为/事实**          | 数千-数万 | 迭代阶段   | 功能迭代效果、转化率、留存对比       | “加不加摘要按钮”对留存的影响           |

**补充说明（了解即可）**：

- **定性研究 (To B)**：样本少，挖得深。关注用户“深层动机、场景与痛点”。
  - *目标*：关注用户“想法、态度、认知”层面（如“你觉得XX功能好不好？”）。
- **定量研究 (To C)**：样本大，用数字说话。验证假设、衡量规模。
  - *行为*：关注用户“实际做了什么”（如“点击了哪些按钮？”“停留了多久？”）。
- **交互设计巧思**：在流程中自然收集反馈（如Google验证码让用户标数据）。

# 三、竞品分析

## 3.1 竞品分析方法论——6步法则 (面试必问)

**Step 1: 明确竞品分析的目的**

- **定位与阶段**：明确产品在市场中处于什么位置和阶段（新产品 or 成熟产品）。
- **竞争目标**：是为了打开新市场，还是在成熟竞争市场中扩大差异化竞争优势。
- **决策支持**：目的是新产品决策、产品规划，还是做市场风险预判。
- *补充背景*：市场早期遵循“CCC”原则（Copy 抄 -> Chao 操 -> Chaoyue 超）。

**Step 2: 竞品具体是什么？选择逻辑是什么？**

- **核心逻辑**：明确这些产品之所以成为竞品的逻辑（非常重要）。
- **三类竞品定义**：

  - **直接竞品**：抢同一拨用户的同一笔预算、同一类场景 (**你死我活**)。
  - **间接竞品**：抢用户“注意力”或“使用场景”，功能有重叠但不是直接对标 (**被动替代**)。
  - **潜在竞品**：现在不是，但用户一旦找到更“灵活”、“便宜”、“强大”的通用AI能力且免费，就可能离你而去 (**防守很难**)。
- **详细对比示例（以AI写作助手为例）**：

| 类型         | 举例                                    | 说明                                                                                                                              |
| :----------- | :-------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------- |
| **直接竞品** | Notion AI、Grammarly、小红书灵感助手    | 功能定位高度重合，都是面向 C 端或轻量 B 端人群，围绕文本生成、润色、校对，是用户会在同一决策链条中比较的工具。                    |
| **间接竞品** | WPS智能写作、飞书文档AI、石墨文档AI助手 | 虽然也有写作能力，但它们的切入点是**办公套件工具内嵌AI功能**，不是单独“写作产品”。但它们抢占了用户日常写作场景。                  |
| **潜在竞品** | ChatGPT (Web端/APP)、讯飞星火、大模型   | 属于“通用大模型”或“开发者工具”，可以被二次封装用于写作场景。用户未来可能用 API 拼接出一个更适合自己的写作助手，而不使用你的产品。 |

**Step 3: 竞品分析6个维度——不超过以下范围**

1. **功能设计**：深入分析竞品的功能，包括三级功能（细致拆解）。
2. **用户体验**：考虑页面布局、色彩、Logo设计、内容质量、交互流畅度等。
3. **盈利模式**：分析竞品的盈利方式，如通过付费会员、广告变现、API调用收费等。
4. **市场推广**：研究竞品的推广策略和渠道（SEO、广告投放、私域运营）。
5. **团队背景**：了解竞品团队的构成（是草根还是大厂背景）、技术优势、资金实力。
6. **企业战略**：分析竞品的企业战略方向和未来规划（是做平台还是做工具）。

**Step 4: 分析数据从哪里来**

- **官方渠道**：通过公司官网、财报、帮助文档等获取信息。
- **行业研究**：参考行业分析报告和智库（挖掘整个市场和用户趋势）。
  - **艾媒网**：[https://www.iimedia.cn/](https://www.iimedia.cn/)
  - **艾瑞咨询**：[https://www.iresearch.cn/](https://www.iresearch.cn/)
  - **行行查**：[https://www.hanghangcha.com/](https://www.hanghangcha.com/)
- **数据平台**：利用百度指数、SimilarWeb、七麦数据等平台。
- **媒体资讯**：关注行业媒体和论坛。
  - **虎嗅网**：[https://www.huxiu.com](https://www.huxiu.com)
  - **36Kr**：[https://36kr.com/](https://36kr.com/)
- **相关人员**：通过调研、访谈销售/客服/前员工获取信息（隐蔽渠道）。
- **亲身体验**：直接注册使用竞品，体验其功能和服务（最直观）。

**Step 5: 竞品分析的工具**

- **最常见**：波特五力模型、SWOT分析。
- **推荐结合**：**竞品画布 (Competitive Analysis Canvas)**。

**Step 6: 最终产出物**

- 完整的竞品分析报告（Word/PDF）。
- 竞品分析PPT（汇报用）。
- 作为产品立项说明书或产品规划材料的一部分。

**💡 Prompt 使用技巧 / 工具推荐**：

1. **发送给 DeepSeek**：开启 R1 (深度思考) + 联网搜索模式 (效果最佳)。
2. **发送给 Manus**：等待执行 (可能会挂，需关注稳定性)。
3. **其他AI搜索/Agent工具**：Flowith、Coze 空间等。

**👀 现实中的竞品分析**：

1. **日常工作**：很少做完整的几十页报告（没时间）。
2. **何时细做**：
   - 负责的产品竞品很多、相对成熟，上新功能时要详细分析。
   - **大模型AI落地刚起步**：竞品少或没有，不确定性高，分析相对简单。
3. **学习重点**：掌握套路，**“面试问的时候要能头头是道地回答”**。

# 四、产品架构

## 4.1 什么是产品架构图？

> *产品架构图是产品经理用来抽象表达一款产品的服务和商业模式的可视化工具。*

1. **结构化**：将业务抽象设计成信息化、模块化、有层级和关联关系的架构。
2. **流程体现**：通过分层、核心功能模块组合、数据和信息流转，体现产品业务流程、业务逻辑、商业模式等。
3. **高效传达**：明确产品边界，指明产品发展方向，实现信息高效传达与对齐。

## 4.2 画图套路：端到端（自下而上）

**核心概念：SaaS平台 - 端到端一体化 (拓展)**

1. **端到端 (End-to-End)**：
   - 从“起点”到“终点”全部打通。
   - **示例**：客户提出需求 -> 平台自动分析 -> 推送给执行团队 -> 完成服务 -> 生成数据报告。(中间没有人工外跳或平台切换)。
2. **一体化**：
   - 系统内功能和模块之间高度集成，不是东拼西凑的工具。
   - **示例**：一个平台既能支持表单收集、流程审批、文档生成、AI分析，也能直接调用API联动第三方系统。

**产品架构图（提取共性）- 层级划分**：

| 层级     | 通用名称                           | 典型功能                                                                                      |
| :------- | :--------------------------------- | :-------------------------------------------------------------------------------------------- |
| **顶层** | **应用层 / 用户层**                | 客户端、员工端、管理端、小程序、微信、H5 等多入口前台                                         |
| **中层** | **业务平台**                       | 拆解为各业务域中心（如合同中心、招生中心、内容中心）                                          |
| **底层** | **技术底座 / 基础服务 / 数据中台** | 存储、消息、调度、权限、账号、云服务、日志、API网关等；`<br>`数据治理、分析、标签、建模等能力 |
| **边界** | **外部集成接口**                   | 聚合接口、集成第三方服务（如CRM、电签、支付、物联网等）                                       |

## 4.3 AI产品的架构变化（AI产品通用架构）

**自下而上层级划分（6层结构）**：

| 层级  | 名称                                  | 核心职能                                                                                                                                                                           |
| :---- | :------------------------------------ | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1** | **应用层 (用户使用端)**               | **最贴近用户体验**：强调交互流畅性、功能可用性和场景覆盖度。`<br>`**服务对象**：C端用户、B端员工、企业客户、外部系统等。`<br>`**形式**：APP、小程序、Web页面、插件组件、H5 SDK等。 |
| **2** | **智能体/Agent编排层 (业务逻辑层)**   | **对接大模型**：实现工具调用、执行任务等。`<br>`**Agent任务编排**：工作流、多轮对话支持；`<br>`**工具调用**：如API、RAG等；`<br>`**管理**：权限控制、访问记录、交互日志分析。      |
| **3** | **RAG能力层 (知识检索增强)**          | **外挂知识库**：解决幻觉、补充私有数据                                                                                                                                             |
| **4** | **模型与推理中间层**                  | **模型管理**：模型选择、路由调度、微调、Prompt管理                                                                                                                                 |
| **5** | **数据与资产层 (Data Layer)**         | **数据供给**：向量数据库、非结构化数据处理                                                                                                                                         |
| **6** | **系统与运维管理层 (System & Infra)** | **算力支撑**：GPU集群、云服务设施、监控报警                                                                                                                                        |

**核心变化**：在原有架构中增加了中间的 **智能体层**、**RAG层** 和 **模型层**。
